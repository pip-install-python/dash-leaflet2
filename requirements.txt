# 2.8.0 — and as in every round, THE NUMBER CHANGING IS THE CACHE BUST.
#
# What 2.8.0 buys, and it is the LEDGER floor: `classify()`, the one vendor
# registry robots.txt is already rendered from, so lib/analytics_tracker can
# delegate instead of carrying a fourth User-Agent list (the one it carried
# filed ClaudeBot — Anthropic's TRAINING crawler — under "search", still named
# the retired anthropic-ai / claude-web tokens, and counted every UA-less or
# library client as a person); and `on_document_read`, one event per corpus
# document served — tier, verdict, bytes, verified vendor — which
# AnalyticsTracker.record_read keeps as the ledger's `reads` table and
# lib/traffic_rollup folds into the v4 `vendors[]` block. Below the floor
# neither name exists and run.py refuses to boot rather than degrade quietly.
# 2.8.1 will write the resolved `policy` on every event; until then it is None
# and the rollup groups it as "default". Nothing here waits on it.
#
# What 2.7.1 buys: llms.txt v2 discovery relations (rel=alternate/describedby
# plus Link headers), the text/plain Accept ramp, and the representation
# digest. What 2.7.0 buys, and this repo needed badly: the prerender H1 dedup.
# Measured here before the bump — all 27 pages served TWO <h1>s to a crawler,
# the injected prerender header plus the document's own, and the home page
# served three. 2.7.0 also stops a page that merely MENTIONS the prerender
# marker string from losing its prerender, and de-doubles the home footer's
# /llms.txt link. run.py's LLMS_PKG_FLOOR refuses to boot below this.
#
# 2.6.1 — the .1 was a CACHE BUST as much as a feature.
#
# The Dockerfile installs deps in their own layer, keyed on requirements.txt's
# BYTES. A commit that touches only lib/ is a cache hit, so pip never re-runs
# and a `>=` floor cannot pull a newer release through the cached layer. That
# is not a theory: the round-2 deploy shipped a lib-only change and stayed on
# 2.6.0 while this file still said `>=2.6.0` — measured live, the prerender
# div came back carrying `hidden`. Two sibling repos hit it before us
# (pannellum found it, emojimart reproduced it). **Changing this number is
# what makes the layer rebuild**, which is why the floor moves for a package
# fix even when the old floor would technically have allowed it.
#
# Corollary, and the reason the CI asserts below now track this number: a
# floor recorded in more than one place drifts, and the copies that drift are
# the ones nothing installs from. Grep the version, not the file.
#
# 2.6.1 itself makes the prerender visible to non-JS consumers: 2.6.0 emitted
# `<div id="dimll-prerender" ... hidden>` and relied on script to unhide it,
# so a reader without JS got an empty box. Verified by direct comparison of
# the two releases against this app.
#
# 2.6.0 is LOAD-BEARING here, not a routine bump: pages/markdown.py passes
# `lastmod=` unconditionally, and that argument only exists from 2.6.0.
# Two things arrive with it.
#
# SITEMAP HONESTY. Before 2.6.0 every <lastmod> was "today", regenerated on
# every crawl — a sitemap that claims 27 pages changed daily is a sitemap
# search engines learn to discard wholesale. 2.6.0 emits the frontmatter
# `lastmod:` VERBATIM and omits the tag entirely when a page declares none:
# truth or silence. Never script those dates from file mtimes, which reset on
# every Docker build and would re-invent exactly the lie this ends.
#
# ICON AUTODISCOVERY. This app never calls `configure_seo`, so until 2.6.0
# Googlebot got a crawler document with ZERO icons while browsers got six
# from templates/index.html. 2.6.0 scans the assets tree — `favicon/` is
# one of its covered directory names — and this site's own art becomes its
# crawler-head identity with no declaration. tests/test_seo_icons.py pins
# both contracts; discovery WARNS rather than failing when it finds nothing,
# so a renamed favicon directory would otherwise be silent.
#
# Earlier steps on the same line, all still required: 2.5.1's Tier-B SEO
# standard (the crawler <title> carrying the site name, /favicon.ico answered

# --- Vendored, docs-only ---------------------------------------------------
# dash-clerk-auth: authentication for the HOSTED documentation site only.
#
# It is deliberately NOT a package dependency and never can be: pyproject.toml
# declares `dependencies = ["dash>=4.1"]` and ships `packages =
# ["dash_leaflet2"]`, so `pip install dash-leaflet2` never sees Clerk, never
# sees lib/auth.py, and never installs this. CI asserts that against the built
# wheel. Enabling it here changes the Render deployment only.
#
# ONE OPERATIONAL RISK, worth knowing before you debug a dead site: the package
# registers a `[dash_hooks]` entry point that Dash auto-imports during EVERY
# `Dash()` construction. Installing it puts Clerk in the boot path of the whole
# documentation site, configured or not — so a broken transitive dependency
# takes down the docs, not just sign-in. Rollback is to comment these two lines
# and redeploy; /admin/control-board fails CLOSED without Clerk, so nothing is
# left exposed by doing so.
#
# 1.0.5 — the last of the three stale-gate cases, and the one on the happiest
# path in the funnel: sign in from this satellite, get sent to the primary,
# come back to the auth-gated page you started on — and the sign-in card is
# still there until you refresh by hand.
#
# The first server render after the return happens BEFORE `__dca_identity`
# exists: the cookie is minted only once ClerkJS completes the handshake and
# the session reaches the server. So the layout resolves anonymous — correctly,
# at that instant — and nothing re-renders when the client finishes a second
# later. It fails SAFE (over-gating, never a leak), which is exactly why it
# survived three releases of sign-out work: nothing leaked, so nothing
# screamed. It was the owner's live report on this host that found it.
#
# 1.0.5 reads the same root-class signal 1.0.4 reads, in the other direction:
# ClerkJS signed-in while the server rendered signed-out means call
# `Clerk.session.getToken()`, POST it to `/api/auth/session` (the identity
# writer that already existed), and reload on a confirmed 200. Same discipline
# as 1.0.4 — fires once per load, waits for a usable token rather than firing
# mid-handshake, and reloads ONLY on success, because reloading after a
# rejected sync rebuilds the same anonymous page and spins.
#
# Both reconciliations now share a `sessionStorage` marker, because the
# in-page fire-once flags die with the load: if the server reports success and
# then still renders the previous state, the reload lands back at the same fork
# and loops. The marker outlives the reload and clears as soon as server and
# client agree. That closes a loop 1.0.4 could reach in principle, not just the
# new path.
#
# 1.0.4 was the mirror case, and the one this site's certification caught: a
# satellite served its ADMIN CONTROL BOARD to a browser that had already
# signed out on the primary.
#
# 1.0.3 revoked the server session on a signed-in -> signed-out TRANSITION, but
# that requires the tab to have observed the signed-in state first. A browser
# that signs out on 2plot.ai and then simply navigates here never had one:
# ClerkJS resolves signed-out immediately, while the server still holds
# `__dca_identity` and has already rendered the page — gated content included —
# off it. 1.0.4 adds fresh-load reconciliation: if ClerkJS resolves signed-out
# while the server rendered the page signed-in, the client POSTs
# `/api/auth/signout` and reloads. The server's own rendered state (the
# `clerk-signed-in` class on <html>) is the only signal available, because
# `__dca_identity` is HttpOnly and the page cannot read it.
#
# Also in 1.0.4: `POST /api/auth/session` and `/api/auth/signout` returned 422
# on EVERY FastAPI deployment, for as long as they had existed —
# `_mount_auth_routes` registered handlers whose `request` parameter was
# unannotated, which FastAPI resolves as a required query field. Inert on this
# host (production is Flask under Docker) and pinned anyway, because
# `lib/backend.py` makes a backend switch one env var away and the failure mode
# is silent: the injected script never inspects the result, so sign-out simply
# stops revoking server-side.
#
# THE SHIM IS STILL HERE, and 1.0.5 is why it was right to keep it: the 1.0.4
# acceptance test never got a clean pass, because the return-trip stale gate
# above interrupted it. Retiring the local handler into that would have made a
# three-way ambiguity out of a two-way one. Retire it once a sign-out AND a
# return trip both pass on one deploy.
#
# lib.auth's `_install_signout_delegation`
# was written expecting to retire here, and deliberately does not: 1.0.4's
# acceptance test IS sign-out behaviour, and removing the local handler in the
# same change would make a failure ambiguous between "1.0.4 does not work" and
# "the shim was load-bearing". They cannot collide — the shim is a click
# handler, the new reconciliation runs once on load — and the POST is
# idempotent. Retire it in the pass AFTER the acceptance test passes.
#
# 1.0.3 was the first half of this: sign out did not reach the server at all.
# The logout handler ran `window.Clerk.signOut()` and reloaded, which
# invalidates `__session` and nothing else, so a signed-out browser kept being
# served every gated page from the `__dca_identity` layer until that cookie
# aged out — up to `session_lifetime_days`, seven days by default. On a shared
# machine the next person inherited the previous user's access for a week.
# 1.0.3 also carried the import fix for the avatar helper, which had inlined
# `quote(svg, safe="/:='? ")` inside an f-string: PEP 701 syntax, a hard
# SyntaxError on 3.10/3.11, and therefore an IMPORT failure. The package
# declares a `[dash_hooks]` entry point Dash resolves at every `Dash()`
# construction, so on this repo's CI matrix (3.10/3.12/3.13) that would have
# taken the whole documentation site down, not just sign-in.
#
# VENDORED ARTIFACT — verify the hash, never the filename or the mtime. This
# has now caught a stale build twice: an early 1.0.4 (sha256 22117b20...) and
# an early 1.0.5 that went stale on sdist doc edits. Both are indistinguishable
# from the good build by name, size at a glance, or date:
#
#   sha256  a2f9062e15a69fc79deeaf76fcf1380907a961978db558b2aa227572cb2b74f3
#           — byte-identical to the authoring repo's dist, and this is the hash
#             of the blob committed here, not just of the working file.
#
# Take the dist artifact whose hash matches. The authoring repo's `main` is
# no longer a trap — the fix branch merged 2026-08-21 (PR #5, `62071e4`), and
# main now carries both the import fix and 1.0.4 — but the rule stands anyway:
# a build is identified by its hash, because both times an artifact and its
# commit were seconds apart in the WRONG order (build, verify, then commit),
# which reads exactly like shipping a pre-fix build and is not.
#
# NOT changed on this bump, and a deliberate decision each application owns:
# `session_lifetime_days` stays at 7 (lib/auth.py passes it explicitly, so the
# value is recorded rather than inherited). `__dca_identity` is a stateless
# signed token — a value captured before sign-out keeps verifying until its
# max-age expires, because the server holds no revocation list. That window is
# the knob; see lib/auth.py for why 7 is the choice here and what would change
# it. Note 1.0.4 narrows what that window costs: the ghost is now revoked on
# the next page load rather than persisting for the cookie's life.
#
# 1.0.2 fixed the avatar race this host was exposed to (components/header.py
# calls `create_clerk_menu`): the injected script resolved the menu with
# `getElementById` at the moment `Clerk.load()` resolved, but Dash mounts that
# menu from a separate /_dash-layout fetch, so whenever Clerk won the race a
# signed-in user sat behind a placeholder avatar for the life of the page.
#
# 1.0.1 widened `clerk-backend-api` to `<8` — see the cryptography floor below.
# 1.0.0 was the first stable release and the first build needing NO local
# patching: 0.9.1 stamps `data-clerk-domain` onto the ClerkJS script tag, and
# 0.9.2 replaced the forbidden `Clerk.openSignIn()` modal with a navigation to
# the primary. That navigation is configured by CLERK_SATELLITE_SIGN_IN_REDIRECT,
# which the package reads from the environment ITSELF — lib/auth.py does not
# pass it through, and an earlier version of this note claimed otherwise.
# Anything older than 0.9.2 needs those patches back.
#
# PYTHON FLOOR: >=3.10 (clerk-backend-api publishes no 3.9 build, so the old
# >=3.9 claim was never installable). That binds the DOCS SITE only —
# Dockerfile is 3.12 and ci.yml's docs matrix is 3.10/3.12/3.13, all clear.
# The dash_leaflet2 PACKAGE keeps requires-python >=3.9: it does not depend on
# this file, and ci.yml's package-python-range job proves 3.9 installs and
# imports the wheel with nothing but dash present.
#
# Still not on PyPI — vendored the same way across every 2plot satellite, so
# the tarball is the distribution channel.
#   Used by: lib/auth.py, components/header.py, /admin/control-board
./vendor/dash_clerk_auth-1.0.5.tar.gz
# SECURITY FLOOR, and the reason dash-clerk-auth had to move first. This pin
# is what `pip-audit` resolves; the vendored tarball's own cap is what gates
# it. clerk-backend-api 5.x declares `cryptography>=45.0.0,<47.0.0`, holding
# cryptography on 46.0.7 — below the fix for all four of GHSA-537c-gmf6-5ccf
# (bundled-OpenSSL OOB read, 48.0.1), PYSEC-2026-3554 (DNS name-constraint
# wildcard escape, 49.0.0), PYSEC-2026-3553 (X.509 chain-build DoS, 49.0.0)
# and PYSEC-2026-3552 (PKCS#7 Bleichenbacher oracle, 50.0.0). Pinning
# cryptography alone could not work: pip returns ResolutionImpossible against
# the <47.0.0 cap. SDK 7.0.0 allows `cryptography<51.0.0`, which is why
# dash-clerk-auth 1.0.1 widened its own declaration to `<8` — the library
# carries the compatibility RANGE, this file carries the security FLOOR.
clerk-backend-api>=7.0.0,<8
cryptography>=50.0.0

# --- Deployment ------------------------------------------------------------
# gunicorn serves the Flask (WSGI) backend in the Dockerfile. The FastAPI
# backend is ASGI and needs uvicorn instead — already pulled in by dash[fastapi].
#
# gunicorn fronts every Flask deployment in this network, so the floor is the
# network's security baseline rather than a convenience: 21.x carried two HTTP
# request-smuggling CVEs (CVE-2024-6827, CVE-2024-1135), both fixed in 23.0.
# This is why markdown2dash is installed with --no-deps above — CI asserts the
# resolved version inside the built image, so a transitive pin can never drag
# the production server back under the floor without failing the build.
gunicorn>=23.0.0
